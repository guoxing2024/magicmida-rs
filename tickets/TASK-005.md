## 项目背景

MagicMida vNext 的主攻线是 **GVM-0 反虚拟化战役**：`gto_launcher` 的 dump 路线已判定为结构性天花板（逐页惰性解密，被动等待 60s 与真实执行 300s 都产出零个新解密页），
所以改走"还原 VM 解释器/handler 语义 → lifter → 整镜像去虚拟化"。Phase 1 的门是"自洽的 ISA 规格书"。

Phase 1 第一批（2026-08-29，报告 `docs/GVM_PHASE1_LAUNCH_20260829.md`）交付了调度循环还原和 172 个 handler 候选，但**自己报了一条必须修正项**：

- `ISA_SPEC_V0` 声称"`0x8f099` → `call 0x8c4c0`，216K+ 次（trace 实证）"，`0x8c4c0` 是主译码器；
- 实测：`0x8c000-0x8cfff` **整页在两个 trace 源里 exec 都是 0**，`0x8c4c0` 和 `0x8f0bb`（`call 0x8c4c0` 所在）exec 都是 0；
- 实测还发现 `0x8f099` 其实是**间接 call**（经槽 `0x12d8c8` → 运行时指针），不是直接 `call 0x8c4c0`；
- `0x8c4c0` 静态存在，表 A/表 B 内容与 dump 一致，但本批 trace 覆盖路径里从未执行。

**这条矛盾没有复核就不许当成已解决**，因为整个 ISA 规格书的核心结论（"主译码器是 0x8c4c0"）就压在这个证据上。
另外有一个已知的统计陷阱：这批 trace 是**基本块入口级**而非指令级，按"页起始地址精确匹配"去统计会得到误导性的 0 —— 之前的 N5 修正（`0x92-0x94xxx` 覆盖）就是这么来的。所以这条矛盾很可能也是同类口径问题，但**也可能不是**。

## 具体要求

1. **先复现原结论**。跑 `verify_baseline_independent.py`，确认 `0x8c000-0x8cfff` 两源 exec=0 这个数字你自己也能得到。得不到就先报告差异。
2. **换粒度重算**。trace 是基本块入口级：一个基本块的入口地址可能在 `0x8b...`，而它的指令流覆盖到 `0x8c4c0`。所以"`0x8c4c0` 从未被执行"和"没有任何基本块的入口地址等于 `0x8c4c0`"是两件完全不同的事。
   至少要回答：有没有基本块的**地址区间**（入口 + 长度，或入口到下一个记录）覆盖 `0x8c4c0`？
3. **查间接 call 的实际目标**。`0x8f099` 是经槽 `0x12d8c8` 的间接 call。在 trace 里找出这个 call 之后实际落到哪个地址，统计目标分布。如果目标不是 `0x8c4c0`，那 `0x8c4c0` 就是另一条未激活路径 —— 这本身是有价值的结论。
4. **给出三选一的定级**，并说明支撑它的具体数字：
   - (a) `0x8c4c0` 确实是主译码器，原"216K+ trace 实证"成立，之前的 exec=0 是统计口径问题；
   - (b) `0x8c4c0` 静态存在但在本批 trace 覆盖的路径里未激活，`ISA_SPEC_V0` 的"trace 实证"标注有误，需降级为"静态推断"；
   - (c) 现有材料不足以判定，需要哪一项额外证据（写清具体是什么，以及是否需要实弹）。
5. **修正落盘**：把结论写进 `docs/GVM_PHASE1_LAUNCH_20260829.md` 的 §3.2（原地修正那一节，不要新建文档），并在 `docs/KNOWN_ISSUES.md` 的 C-3 条目下追加最终定级。
