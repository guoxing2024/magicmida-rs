## 3. P0-2401：栈合同方向正确，但验证证据无效

### 3.1 文档推导本身

当前合同采用：

```text
入口 rsp ≡ 8 mod 16
sub rsp, 0x38
call 前 rsp ≡ 0 mod 16
outgoing arg4/arg5/arg6 = [rsp+0x20]/[rsp+0x28]/[rsp+0x30]
```

这套算术方向与 Windows x64 调用模型一致，`ThunkArgs7` 的 blob offsets 也与寄存器/栈参数映射一致。该部分只能作为 design candidate，不能自动升级为 P0 pass。

### 3.2 `thunk7_abi_stdout.txt` 与报告结论直接冲突

原始输出实际为：

```text
callee rsp mod 16 at entry = 0 (expect 8)
arg0 ... arg6 全部打印
ABI ROUND-TRIP FAIL
ABI_EXIT=1
```

因此 worker 报告中的“7 参数回传 PASS”不成立。参数值到达并不等于栈对齐验证通过；该 stdout 必须按 FAIL 记账。

### 3.3 `thunk7_rsp_test.c` 没有真正记录 rsp

源码中的探针字节：

```text
4D 89 63 48
```

REX.WRB 中 `R=1`，ModRM `63` 的 reg 字段因此是 `r12`，实际语义是：

```text
mov [r11+0x48], r12
```

不是：

```text
mov [r11+0x48], rsp
```

后者应使用 `49 89 63 48`。所以 `thunk7_rsp_stdout.txt` 的 `call pre-rsp mod 16 = 0` 不是有效的 rsp 观测证据，不能覆盖 3.2 的 ABI FAIL。

### 3.4 ml64/dumpbin 证据边界

`thunk7.obj`、`verify7.obj` 和 dumpbin 只能证明某组字节能被汇编/反汇编；不能证明：

- 目标函数实际收到的第 5–7 参数位置正确；
- callee entry rsp 对齐正确；
- rsp 探针记录的是 rsp 而非其他寄存器；
- 远程 WPM/CreateRemoteThread 执行行为正确。

WO-2401 P0 必须重新提供可信的本机 harness 证据后才能重新审查。
