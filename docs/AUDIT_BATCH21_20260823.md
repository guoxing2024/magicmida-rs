## 3. P0-2101：TLS 合同的剩余缺口

### 3.1 0x20 C/Rust layout 已通过静态审查

当前 C header、Rust FFI 伪代码和 fixture 均列出：

```text
magic +0x00
active +0x04
seq +0x08
flags +0x0C
token_va +0x10
unknown_code +0x18
size 0x20
```

`mida_probe_tls_mark` 也已加入 Rust 声明；旧 `reserved`/0x18 版本和 `PROBE_TLS.with` 残留已清理。这部分条件通过，但只是 design/fixture 层。

### 3.2 begin stale 检查没有覆盖 stale token

`mida_tls_begin_check` 当前只检查：

```text
magic 损坏
active != 0
flags != 0 或 unknown_code != 0
```

它没有检查 `active == 0 && token_va != 0`。如果上一候选在 clear 前异常退出、clear 部分执行失败，旧 `token_va` 仍可能残留，而 flags/unknown_code 恰为零；下一次 begin 会接受并覆盖旧 token，失去 fail-closed 证据。必须冻结 `token_va == 0` 的 begin 前置要求，或明确可验证的 token 清理/故障状态。

### 3.3 accessor 与异常上下文边界仍属设计假设

设计让 VEH 调用 `mida_probe_tls_snapshot()`、`mida_probe_tls_mark()`，而 SEH filter 在异常分派上下文直接读 C TLS。尚无：

- C accessor 的不可失败/不可重入合同；
- snapshot 指针有效期与 `clear` 后失效规则；
- VEH 中函数调用是否允许、函数本身 fault 时如何 fail-closed；
- TLS slot 初始化失败、线程退出和 DLL 卸载期间的行为合同。

这些可以留到 Windows V10，但必须在实现前合同中显式列为未验证，不得以 C11 fixture 编译替代。

## 4. P0-2102：V2 envelope 仍有实质性安全缺陷

### 4.1 独立 ASan 复现：profile string scan 越界

我用 MSVC x64 `/std:c11 /W4 /WX /fsanitize=address` 编译临时 hostile harness，令：

```text
params_bytes = 256
profile_id_off = 255
blob[255] = 'X'（无 NUL）
```

运行 `mida_v2_envelope_check` 得到：

```text
AddressSanitizer: stack-buffer-overflow
READ of size 1
WO-2102-v2-envelope-fixture.h:137
```

根因是循环条件检查的是 `p - blob < params_bytes`，但实际访问为 `p[i]`；当 offset 靠近尾部时，没有保证 `offset + i < params_bytes` 后再读。该 fixture 不能作为“完整拒收矩阵”或“panic-free/overflow-free”证据，P0 必须退回。

### 4.2 `expected_hooks` 迭代器宽度没有冻结

fixture 用 `unsigned int i` 遍历 `uint64_t expected_hooks`。即使 `expected_hooks * 8` 的 checked multiplication 通过，`expected_hooks > UINT_MAX` 时循环变量可能回绕；合同也没有独立 MAX_EXPECTED_HOOKS 上限。必须冻结上限并用 checked `size_t`/`uint64_t` 迭代语义。

### 4.3 header trust boundary 没有真正进入 runtime ABI

7 参 V2 签名只有：

```text
params, params_bytes, out_runtime_sha256, out_runtime_sha256_len,
out_attestation_json, out_attestation_len, out_attestation_written
```

但设计/fixture 的安全判定额外依赖：

```text
expected_blob_base_va
header_readable
blob == params
```

这些不是入口参数，也不在 0x48 结构中。runtime 无法自行比较 `params` 与 controller 记录的 base，也无法把外部 `header_readable` 布尔值当作真实页可读性证明。必须选择一种唯一可执行方案：将 provenance nonce/base 放入 envelope 并由 runtime 校验，或明确“header 可读性是硬信任边界，坏指针行为为进程终止而非返回 HeaderFault”；不能两种语义并写。

### 4.4 surface entries 的引用语义不一致

报告称“全部引用字段改 self-relative offsets”，但 `expected_surfaces_off` 指向的数组元素仍是 target-local 绝对 VA。若这是有意设计，必须明确它是唯一例外并冻结 canonical/provenance/string ownership；若要求所有引用 self-relative，则数组元素也必须改为 offsets。

当前 fixture只验证数组元素位于 `[expected_blob_base_va, expected_blob_base_va + params_bytes)`，没有验证每个 surface string 的 NUL 和实际区段归属；且 base+size 的加法没有单独 checked overflow。该部分不可关闭 P0。

### 4.5 7-arg thunk 合同仍不够可实现

文档给了 arg0..arg6 表格，但没有冻结 `THUNK_CODE_7ARG` 的实际机器码、栈槽偏移、shadow space、stack alignment、callee cleanup 和 `ThunkArgs7` 的确切内存布局。7 参数在 Windows x64 下跨寄存器/栈传递，不能只写“第 7 参走栈”就算 ABI 完整。
