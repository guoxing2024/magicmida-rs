## 3. P0 阻断发现

### P0-1501-1 — untrusted params decode 可超大分配

文件：`crates/antidebug-runtime/src/walker_protocol.rs:484-490`。

`from_blob_bytes` 读取 header 后直接执行：

```rust
Vec::with_capacity(hdr.candidate_count as usize)
```

它在 `validate()` 前执行，也没有先检查 `candidate_count <= MAX_CANDIDATE_COUNT`、header/total bounds 或实际 buffer 上限。恶意 mapping/blob 可令 decoder 先申请接近 `u32::MAX` 的容量，导致 OOM/进程终止；这违反模块自称的“hostile input fail-closed”。

### P0-1501-2 — untrusted result decode 可 panic 或资源耗尽

文件：`walker_protocol.rs:1212-1246`。

`parse_section` 在 `validate_layout()` 前使用攻击者提供的 `result_stride` 和 `result_count`：

```rust
payload_len = result_count * result_stride;
Vec::with_capacity(result_count as usize);
bytes[pos..pos + PROBE_RESULT_BYTES]
```

问题：

1. `result_stride = 0`、`result_count` 极大时，payload 长度为 0，但会尝试超大 `Vec`；
2. `result_stride < PROBE_RESULT_BYTES` 时，`end` 检查可能通过，随后固定 40-byte slice 越界，触发 panic；
3. parse 函数文档明确写“transport only; no validation”，但其内部仍直接分配和切片，不是 panic-free parser。

**修复门：** decode 必须在任何 allocation/slicing 前检查 magic/version/section_bytes 上限、fixed stride、results offset、count 上限和 checked region；所有 hostile fixture 需用 `catch_unwind`/无 panic 测试证明。

## 4. P0-1502-1 — VEH handler 顺序与闭环证明相互矛盾

文件：`docs/WO-1301A-IMPL-walker-execute-design.md:236-298`。

文档同时规定：

- `AddVectoredExceptionHandler(first=1)`，walker handler 最先调用（`:288`）；
- walker 对所属 probe fault 直接修改 RIP 到恢复桩并返回 `EXCEPTION_CONTINUE_EXECUTION`（`:255-273`）；
- 又声称保护器在 walker 之后仍有机会先处理并完成解密（`:290-296`）。

这三条不能同时成立。walker 一旦在首个 handler 中 `CONTINUE_EXECUTION`，后续保护器 VEH 不会继续获得该异常。于是 Route α 的“保护器解密成功 → Type B”路径被 walker 首先截断。若改成 `CONTINUE_SEARCH` 让保护器先处理，又必须重新证明 walker 收口、未处理异常和保护器链顺序。

这是 P0，不是实现细节。必须冻结唯一顺序和控制流，并给出 handler registration/dispatch 的可测试契约。

## 5. P0-1502-2 — probe 成功状态的伪汇编错误

文件：`docs/WO-1301A-IMPL-walker-execute-design.md:217-234`。

成功路径写的是：

```text
mov rax, [va]
...
mov rax, [va+8]
mov al, 0
```

`mov al, 0` 只清除 RAX 低 8 位，不能把包含读取数据的 RAX 变成 0。探针循环按 `RAX==0` 判断成功，因此除非高位恰好为零，成功读取会被误判为异常。应定义专用状态寄存器/返回槽或使用完整清零指令，并明确 Windows x64 ABI 下输出缓冲区、volatile register、shadow space 和恢复桩返回约定。

当前只是设计文档，不能据此派发实现。

## 6. P1-1502-3 — 未知异常被收口而不是 fail-closed abort

文件：设计文档 `:266-273`、`walker_protocol.rs:108-121`。

设计把未知异常写入 TLS 后也跳恢复桩、返回成功式闭环；此前审计门要求“非预期异常立即 abort”。未知异常可能是 breakpoint、illegal instruction、stack fault 或其它非探针语义。必须拒收并终止 walker 状态，不能静默分类后继续探针。

## 7. P1-1503-1 — digest vectors 2/3 仍是占位值

文件：`docs/WO-1503-attestation-v2-schema.md:236-271`。

Vector 2 和 Vector 3 的 digest 是明显伪造的重复序列，并在文档中承认“占位格式”。这违反 WO-1503 的明确交付条件“3 个固定 digest vectors”。P0-B 不能标记关闭，schema 只能是冻结候选。

## 8. P1-1503-2 — canonical JSON 未定义 bool 编码

文件：`docs/WO-1503-attestation-v2-schema.md:193-217`。

v2 顶层和 round ledger 含多个 `bool` 字段，但 canonicalization 数字规则只定义整数/double，没有定义 JSON `true`/`false` 的编码与拒收规则。实现者无法从当前合同生成唯一 preimage。

## 9. P1-1504 — lifecycle 状态命名漂移

文件：`docs/WO-1504-timeout-orphan-lifecycle.md:24-45,82`；对照 WO-1503 `:175-189`。

状态机正常路径使用 `reclaimed`，状态表/Orphan 封闭集合使用 `os_reclaimed`。正常完成的“marked reclaimed”没有对应冻结枚举。必须统一为一个状态集合，并同步 ledger、Orphan、acceptance 语义。

## 10. P1-1505 — artifact digest 绑定方案循环且与 ABI 设计冲突

文件：

- `docs/WO-1503-attestation-v2-schema.md:286-294`
- `docs/WO-1505-loader-abi-matrix.md:68-79,99-108`

1503 要求 controller 计算 DLL digest 后“写入 init params 下发给 runtime”；1505 同时规定 `MidaInitParams 不扩展`。当前真实 `MidaInitParams` 也没有该字段。

此外，1505 写“构建时将 runtime DLL 文件字节 sha256 注入 runtime DLL”。若哈希覆盖最终 DLL 全部字节，则把 digest 写进 DLL 会改变被哈希字节，形成自引用/循环。必须改为：外部 manifest/authority digest 作为唯一权威，或明确排除字段/两阶段 artifact 规则；不能把自嵌入最终文件哈希当证据。
