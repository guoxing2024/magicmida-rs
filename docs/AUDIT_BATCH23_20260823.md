## 3. P0-2301：7-arg thunk 栈 ABI 仍错误

### 3.1 当前合同的栈槽错位

当前 fixture 与文档冻结：

```text
sub rsp, 0x40
mov [rsp+0x28], arg4
mov [rsp+0x30], arg5
mov [rsp+0x38], arg6
call rax
```

但 Windows x64 下，thunk 由 caller 的 `call` 进入时，入口 `rsp` 通常为 `8 mod 16`。执行 `sub rsp,0x40` 后，call 前 `rsp` 仍为 `8 mod 16`；再次执行 `call` 会使目标函数入口对齐状态错误。`0x40` 是 16 的倍数，不能修正入口的 8-byte return-address 偏移。

对于 7 参数，call 前应提供 32-byte shadow space 加 3 个 8-byte stack arguments；在保持 call 前 16-byte 对齐的前提下，frame/slot 必须按真实 caller rsp 推导，不能直接把第 5–7 参数放到当前文档的 `+0x28/+0x30/+0x38`。

### 3.2 当前合同把 home/shadow 与 outgoing arguments 混为一谈

文档把 `[rsp+0x28/0x30/0x38]` 同时称为“第 5–7 参数 home 槽”。Windows x64 的 shadow space 是被调函数可使用的前 32 bytes；第 5 及以后参数位于 caller 为该 call 准备的 outgoing argument area，不能用“home 槽”术语掩盖偏移来源。必须明确：

- thunk 入口 rsp 的模 16 状态；
- thunk 自建 frame 的精确大小；
- call 前目标函数看到的参数槽偏移；
- 32-byte shadow space 与 3 个 stack arguments 的边界；
- ret 后 frame 恢复和 caller cleanup；
- `ThunkArgs7` blob offsets 与 call-frame offsets 的映射。

### 3.3 “ml64/dumpbin 实测”证据的边界

`thunk7.obj`/`verify7.obj` 能证明 assembler 接受并产生某组字节；它不证明目标函数收到正确的 7 个参数，也不证明远程线程入口、栈对齐、shadow space 和 `CreateRemoteThread` 执行行为。当前没有一个可运行的 Windows caller harness 验证参数值回传，因此 P0 仍开放。
