## 3. 审计发现

### P0-A — VEH 只分类，不提供可继续执行的异常恢复

位置：设计文档 §3.3-§3.4，约 `:191-235`。

文档规定 walker VEH 对 `STATUS_GUARD_PAGE_VIOLATION` 与 `STATUS_ACCESS_VIOLATION` 都返回 `EXCEPTION_CONTINUE_SEARCH`，只设置 TLS flag，然后声称由 `walker_inner` 决定重试/跳过。这个控制流不闭环：

1. 若保护器 VEH 没有处理 guard，异常链继续到未处理路径，不能回到 `walker_inner`。
2. 对真实 AV，若没有更后置 handler 处理，进程会终止；`walker_inner` 没有机会读取 `av_seen` 后“跳过该候选”。
3. 文档标题写“上下文修正”，但没有定义 `EXCEPTION_POINTERS.ContextRecord` 的任何修正，也没有专用 probe stub、故障指令长度、RIP/RAX 恢复规则。
4. `first=1` 是进程级 VEH。虽然声明 TLS，但没有明确按当前 walker 线程、walker active phase、故障地址/指令地址过滤，存在观测和处理非 walker 异常的风险。

**阻断要求：** 在设计重新联审前，必须选定一种真实且可测试的模型：

- 用专用 native probe stub + 明确的异常上下文恢复协议；或
- 用 Windows SEH `__try/__except`/等价 FFI 边界包住单条探针并明确保护器 VEH 链行为；或
- 给出等价机制的 x64 指令级恢复证明。

必须定义：异常归属判定、guard/AV/未知异常的返回路径、嵌套异常、handler 卸载时机、失败时如何保证不让进程继续执行未知 RIP。不能再用“设置 TLS 后由上层决定”替代异常控制流。

### P0-B — schema v2、canonical digest、迁移分派均未定义完整

位置：设计文档 §7.2-§7.5，约 `:411-449`。

当前文本只有字段草图，不是可实施 wire contract：

- 没有完整的顶层 `RuntimeAttestationV2` 类型或 tagged/untagged dispatch 算法；`schema_version`、现有 v1 的 `schema` 字段和 `WalkerAttestation.schema_version` 的关系不清楚。
- `RoundLedger`、`ProbeSummary`、`Orphan` 没有字段定义、类型约束、上限和序列化规则。
- `canonical_encoding: "json-c14n"` 只是字符串，没有定义 key 排序、数字格式、Unicode、数组顺序和空值规则。
- `record_digest` 被描述为“本记录 canonical 编码后的 sha256”，但没有定义是否排除 `record_digest` 字段；按字面会形成自引用循环。
- `Provenance` 仍是独立 v1 结构；Walker 的 target identity、runtime artifact digest、round/orphan 证据如何进入唯一 acceptance record 没有可执行的合并/消费接口。

**阻断要求：** 先产出冻结的 v2 wire schema：完整 Rust 类型/JSON fixture、版本分派、v1 保持拒绝未知字段、v2 round-trip、digest 预像字段排除规则、canonicalization 测试向量、rollback/旧 consumer 行为。未完成前不得派发 runtime/CLI 的 schema 改造。

### P1-A — params/result 的边界验证算法不完整

位置：§2.2、§2.4，约 `:89-115`、`:126-144`。

文档给出 offset/length 字段，但没有写成可测试的 checked arithmetic 合同。缺失至少包括：

- `header_bytes == 0x40`、`candidate_off == 0x40` 的固定约束；
- `candidate_count` 上限；
- `candidate_off + candidate_count * candidate_stride <= blob_total_bytes` 的 checked 运算和整数溢出拒绝；
- `blob_total_bytes` 与实际 `VirtualAllocEx`/写入长度的一致性；
- `result_bytes`、`results_off`、`result_count * result_stride` 的 checked bounds；
- `result_stride == sizeof(ProbeResultV2)`、`results_off >= header_size`；
- x64 candidate VA canonicality、页跨界 `probe_span` 合同；
- 结果 header 初始化、并发可见性/完成标志写入规则。

这不是“实现时再补”的普通细节，而是 wire protocol 的安全边界。

### P1-B — named section 不能只靠随机 nonce 宣称防抢占

位置：§2.3-§2.5，约 `:117-159`。

当前方案只写了 `Local\\...-{pid}-{nonce}`、CSPRNG nonce、当前用户 DACL 和 target 侧 `OpenFileMappingW`。缺少：

- mapping header 中的 nonce、target PID、controller/session owner、section size 的回显与 controller 校验；
- 精确的 ACL/SecurityDescriptor 构造和失败行为；“当前用户”不等于“本次 controller”；
- controller 是否 `MapViewOfFile` 初始化 header、何时读取结果、controller-side view 的 unmap 顺序；表格中的“若映射”不是协议定义；
- params blob 的 `result_nonce`/`result_bytes` 是否在写入后变为只读，及其完整性保护；
- OpenFileMapping 成功但打开了同名错误 section 时的拒收规则。

随机 nonce 是冲突概率降低，不是 mapping identity proof。必须补 header handshake + owner/target/session binding + controller mapping 状态机。

### P1-C — loader 对位部分成立，但文档有事实错误且不能宣称现成支持

位置：设计文档 §4，约 `:245-287`；真实代码见上述 2.1。

“复用真实 `resolve_mida_exports_remote`”方向正确，但当前代码并未支持 Walker：wanted 列表仍为 3 项，`MidaExports` 也仍是 3 字段，runtime 也没有 Walker 导出。文档 `:281` 还写“现含 initialize/shutdown”，与真实三字段不符。

此外，文档要求 `runtime_module_sha256`/artifact digest binding，而 runtime 当前 attestation 仍填 `adr4-foundation-unbound` 占位值。必须在实现工单中明确 digest 的权威来源、生成时机、controller 复核和 attestation 绑定，不得把 authority.verify_file 口头复用当作 target 内 evidence。

### P1-D — TimedOut orphan 只有不可释放规则，没有可审计生命周期

位置：§5.4-§5.5，约 `:338-355`。

禁止释放远程可触碰资源是正确的；但“最终由 target 进程退出回收”没有 controller 侧持久化 orphan record、target exit 观察、回收确认、异常退出标记和后续禁止重入的具体机制。尤其 timed out 后不能依赖 target 返回 attestation 来写入账本。

需要定义 controller-owned durable ledger：创建、timeout、target-exit observed、reclaimed/OS-reclaimed、unobservable 四态，及其与 `WalkerAttestation` 的关系。若没有 target exit 观察能力，最终状态必须保持 `unconfirmed`，不能写成已回收。
