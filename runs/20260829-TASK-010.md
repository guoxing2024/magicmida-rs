## 〇、结论摘要

1. **ntdll+0x160bd8 定性**：磁盘字节 = `F6 04 25 08 03 FE 7F 01` = `test byte ptr [0x7FFE0308], 1`，位于 **NtContinue** 系统调用 stub（NtContinue 导出 RVA=0x160bd0，stub 偏移 8 处）[已验证：dumpbin disasm + exports]。该指令**正常情况下不可能 AV**（0x7FFE0308 是 KUSER_SHARED_DATA，恒映射可读）。而 21:1x 风暴的 `target=0x204` 与干净指令读 [0x7FFE0308] 的预期 target（0x7FFE0308）**矛盾** → debuggee 内存中该 RIP 处的字节**被改写过**。ScyllaHide 恰好在该地址（0x7ffa95400bd0 = ntdll+0x160bd0）hook NtContinue（`scylla_hide.log` 明示），风暴 RIP = hook 覆盖区尾部。→ **21:1x 风暴是 ScyllaHide NtContinue-hook 区域故障**（hook 尾部 `jmp rax` 落到 rax=0x204 → 执行 AV），不是 Themida 的"映像基址自检"。
2. **`AccessViolation { address }` 字段语义**（引擎代码确证）：`address` = `ExceptionRecord.ExceptionAddress` = **故障指令地址**；`target_address` = `ExceptionInformation[1]` = **被访问地址**。报告口径混淆，两者不同 [已验证：windows_debugger.rs:3250,3263-3272；debugger.rs:72]。
3. **基址漂移机制**：样品 DllCharacteristics=0x60 = `DYNAMIC_BASE | HIGH_ENTROPY_VA`（[已验证] PE 头），EXE 基址是**每次进程创建的独立 ASLR 掷点**（47-bit 高熵空间）。0x7ff6c0c60000 vs 0x7ff799fc0000 差 3.6GB 是正常掷点差。**同基址成功与失败并存**（04:0x 时段同基址 0x7ff6c0c60000 下 attempt3/try1 成功、fixed2 失败）→ 基址值**不是**因。
4. **壳基址依赖**：既有静态产物（step1 静态输出）**未发现** Themida/WinLicense 的"映像基址自检 / 基址相关解密密钥"证据。.winlice VM handler 前 64K 全部为帧相对寻址（r12/rbp 相对），.boot 加密（高熵），引擎 plugin 仅把 runtime_base 用于 RVA 换算。
5. **对照分析**：04:0x 风暴（exc=target=0x1108e3761a0, exc_type=8, 同元组 322 万次）与 21:1x 风暴（exc=ntdll+0x160bd8, target=0x204）**不是同型**：前者是 VM 跳到未映射地址的**取指环**，后者是 **ScyllaHide hook 区域故障环**。两时段都发生在 text-poll 阶段、都无 guard、都被引擎吞掉。
6. **引擎结构缺口（本次调查最重要的新发现）**：text-poll 阶段**没有任何风暴终止机制**：
   - guard 未装时 `decide_av_oep` 无条件 `AvOepAction::Continue`（av_oep_handler.rs:162-167）→ 风暴计数器 `unrelated_av_streak` 永不递增（只在 guard_installed && NotGuarded 分支，av_oep_handler.rs:232）；
   - `text_poll_start` 在**每个事件**上重置（mod.rs:1140）→ 30s idle 超时（mod.rs:1159-1164）在连续 AV 流下**结构上永不触发**；
   - .text-stable 判定（mod.rs:1214-1217）依赖壳完成解密，壳卡在 AV 环 → 永不达成。
   - **任何** constant-AV 环在 text-poll 阶段都必然 0% 收敛，直到外部超时/杀进程。
7. **最终定性：(c) 共因表象 + 引擎侧缺口**。基址差异与 AV 风暴**不是因果**，都是"会话运行时布局/时序熵"这一第三因素的表象；而"9/9 确定性失败 vs 1/5 随机失败"的差异，主要由**引擎缺口的放大器作用** + 21:1x 时段壳恰好稳定进入 NtContinue-hook 故障环（会话状态相关）造成。下一步建议：**(b)+(c) 开引擎修复工单（text-poll 风暴终止），暂不建议纯靠"重启后重试"当解法**（重启不改变引擎缺口，只改变运气）。

## 一、验收标准逐条对照

### 标准 1：ntdll+0x160bd8 定性结论（含工具/方法与可信度）

**工具**：本机 VS2022 `dumpbin.exe`（`C:\Program Files\Microsoft Visual Studio\2022\Professional\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\dumpbin.exe`）对 `C:\Windows\System32\ntdll.dll`（版本 10.0.26100.8972，与 006R 基线 `ntdll.dll 0x7FFA952A0000` 同一 boot 下加载的是同一份磁盘文件 [已验证：TASK-006R 基线 vs 本机文件版本一致]）。

**反汇编（`/DISASM /RANGE:0x180160b80,0x180160c30`）**：

```
0000000180160BD0: 4C 8B D1          mov  r10,rcx
0000000180160BD3: B8 43 00 00 00    mov  eax,43h          ; NtContinue syscall number
0000000180160BD8: F6 04 25 08 03 FE 7F 01  test byte ptr [000000007FFE0308h],1  ; <== 风暴 RIP
0000000180160BE0: 75 03             jne  0000000180160BE5
0000000180160BE2: 0F 05             syscall
0000000180160BE4: C3                ret
0000000180160BE5: CD 2E             int  2Eh
0000000180160BE7: C3                ret
```

**导出表**：`283  112 00160BD0 NtContinue`；`284  113 00161800 NtContinueEx`；相邻 `00160BF0 NtQueryDefaultUILanguage`。

**结论（分级标注）**：
- [已验证] `ntdll+0x160bd8` 磁盘字节是 `test byte ptr [0x7FFE0308], 1`，属 **NtContinue** syscall stub（stub 起点 +0x160bd0，+0x160bd8 是第 3 条指令）。
- [已验证] 该指令读 KUSER_SHARED_DATA+0x308，该页恒映射可读，**干净字节下不可能触发 AV**。
- [已验证] 21:1x 风暴 exc=0x7ffa95400bd8 = ntdll(0x7ffa952a0000)+0x160bd8，恒定。
- [已验证] `target=0x204` 与干净指令读 [0x7FFE0308] 的预期 target 矛盾 → **debuggee 该 RIP 处的字节不是磁盘字节**（被改写）。
- [已验证] `scylla_hide.log`（21:56:09，最后一次 attempt 的注入日志）：`ApplyNtdllHook -> _NtContinue 00007FFA95400BD0` + `Hooking NtContinue` → **ScyllaHide 恰好 hook 了 0x7ffa95400bd0（=ntdll+0x160bd0）**，即风暴 RIP 落在 hook 覆盖区。
- [推断] 风暴指令 = hook 尾部（如 10 字节 `mov rax,imm64; jmp rax` 的 `jmp rax` 落在 +0x160bd8），rax 被壳/调用方残留为 0x204（一个句柄值），jmp 到 0x204 → 执行 AV → 引擎吞掉重试 → 无限环。**该微指令确切字节无法实锤**（3.5GB 原始风暴日志已被 worker 清理，不在盘上），但"RIP 在 hook 覆盖区 + target 为低值句柄"的组合与 hook 故障完全自洽。[存疑：确切微指令]
- [存疑] 为什么 rax=0x204 / 为什么本时段恒定：需要新 trace 才能定性（超出只读范围 → 按停止规则上报，见 §七）。

### 标准 2：`AccessViolation { address }` 字段语义从引擎代码确证的引用行

- `crates/core/src/windows_debugger.rs:3250`：`let addr = exc.ExceptionRecord.ExceptionAddress as u64;` → 进入 `DebugEvent::AccessViolation { address: addr, ... }`。
- `crates/core/src/windows_debugger.rs:3263-3272`：`target = ExceptionInformation[1]`（被访问地址）；`exc_type = ExceptionInformation[0]`（0=read/1=write/8=execute）。
- `crates/core/src/debugger.rs:72`（结构体 doc）：`/// Address of the faulting instruction.` → **`address` = 故障指令地址**；`debugger.rs:74-75`：`/// The target address that was accessed. target_address` → 被访问地址。
- `crates/cli/src/unpacker/av_handler.rs:45`：日志 `exc={exception_addr:#x}, target={target_address:#x}` → **报告里的 `exc=` 是故障指令地址（=ExceptionAddress），`target=` 是被访问地址（=ExceptionInformation[1]）**。

**结论**：`exc=0x7ffa95400bd8` 是**故障指令地址（RIP）**，不是访问目标。TASK-006R 报告把两者混为一谈（"AV 在 ntdll 内部反复触发"表述方向正确，但把 exc 当"访问目标"的口径是错的）。[已验证]

### 标准 3：基址漂移机制的机制清单 + 可能性评估

样品 PE 头（`lab/xx21b_resume/redump2/input.bin`，即 78009803… 保护样品）：ImageBase=0x140000000，SizeOfImage=0xd28000，**DllCharacteristics=0x60 = DYNAMIC_BASE|HIGH_ENTROPY_VA** [已验证：python struct 解析 PE 头]。

| # | 机制 | 评估 |
|---|---|---|
| 1 | **每次 CreateProcess 的独立 ASLR 掷点**（boot-seed + 每进程熵；HIGH_ENTROPY_VA 下 47-bit 空间 64K 对齐随机） | **最可能**。0x7ff6c0c60000 与 0x7ff799fc0000 差 3.6GB，处于高熵掷点正常范围。同一 boot 内两个时段 = 两次不同掷点。**同 boot 内 9/9 同基址**可由"每进程熵池随时间缓步推进、相邻创建得到相近掷点"解释。[推断] |
| 2 | 每 boot ASLR 种子 + 父进程上下文确定性 | 部分成立（同一 boot 内同父进程多次掷点相近），但 04:0x 与 21:1x 是**同一 boot**，种子相同，基址仍不同 → 必有每进程/时间熵分量。[推断] |
| 3 | ASLR 池耗尽/地址空间碎片 | **不可能**：每次新进程是全新 47-bit 空间，13.8MB 映像映射时无碎片；死进程残留不跨进程。[已验证（机制层面）] |
| 4 | 临时映射残留 | **不可能**：进程地址空间不复用死进程。[已验证（机制层面）] |
| 5 | 进程创建参数差异（启动方式 cmd/PowerShell/bash 不同） | 21:1x 用了 3 种启动方式仍 9/9 同基址 → 启动方式不改变掷点。[已验证（现象层面）] |

**关键反证**：04:0x 时段**同基址 0x7ff6c0c60000 同时出现成功与失败**（attempt3 03:58 成功、try1 04:09 成功、fixed2 04:07 失败，全部同基址，见 `lab/xx21b_resume/redump2/unpack_attempt3/fixed2/try1.stdout.txt` 的 CreateProcess 行）→ **基址值不是成败决定因素**。[已验证]

### 标准 5：最终定性 (a)-(d) + 下一步建议

**定性：(c) 共因表象（附带引擎结构缺口）。**

理由链：
1. 基址不是因（标准 3 反证：同基址成败并存）。
2. 基址不是果（风暴发生在 ntdll hook 区，与基址值无算术关系）。
3. 基址与风暴都是"会话运行时布局/时序熵"（第三因素）的表象：04:0x 时段壳的 VM 初始化偶发落到未映射地址（VM 取指环）；21:1x 时段壳的异常分发偶发/恒定地穿过被 ScyllaHide 改写的 NtContinue stub（hook 故障环）。
4. 引擎缺口把"偶发环"放大为"确定性 0% 收敛"：text-poll 阶段无风暴终止（guardless 吞掉 + 每事件重置 idle 计时），任何 constant-AV 环都只能等外部超时。
5. 21:1x "9/9 确定性" vs 04:0x "随机"：同一引擎缺口下，04:0x 时段壳大部分运行不进入环（2/3 成功），21:1x 时段壳每次都进入同一 hook 故障环（会话状态/时序差异）。基址值不参与因果。

**下一步建议**：
- **(b)+(c) 优先**：开引擎修复工单——text-poll 阶段增加风暴终止机制（等价于现 guard 路径的 `unrelated_av_streak` 风暴计数 + Break，或对恒同 AV 元组计数达到阈值后强制 .text-stable 失败走 fail-closed dump 路线）。这是把"9/9 确定性失败"变成"可收敛/可失败关闭"的关键，且纯离线可改、可单元测试。
- **附带的 ScyllaHide NtContinue-hook 交互**建议单独立项调查（hook 尾部 `jmp rax` 落到句柄值 0x204 → 疑似 ScyllaHide 与此 ntdll 构建（10.0.26100.8972）的 hook 兼容性或壳-注入竞态）；需要新 trace 定性 → 按停止规则 STOP，另开实弹工单。
- **不建议把"重启后重试"当解法**：重启只改变运气（可能换回 0x7ff6… 基址 + 04:0x 式随机分布），不改变引擎缺口；即便重启后成功一次，仍是 1/5 级随机成功率。可作为低成本附带尝试，但不应是唯一路线。

## 三、对照分析：04:0x 与 21:1x 是否同型

| 维度 | 04:0x 时段 | 21:1x 时段 |
