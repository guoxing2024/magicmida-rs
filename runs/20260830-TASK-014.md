## 3. 诊断结论：为什么 XX-10-A 在本样品 0 覆盖

### [已验证] 静态层面（离线证据）
1. **磁盘 IAT 区与 .text 加密**：样品 `.text`(rva 0x1000) 头 32 字节 `e915cc5c6615239754074100a9fafd94...`（高熵加密）；IAT 区(rva 0x1136e0) slot0 raw `0x706a1e96cba6a11b`（加密）。R5 运行时解密态 `.text` 头为 `c30f1f400066662e0f1f8400000000004157...`（OEP scan head_hex）→ **192 站点与槽值只能运行时采回**。
2. **原 PE 磁盘导入表明文 9 模块 9 函数**（bootstrap 子集）：kernel32.GetModuleHandleA / ADVAPI32.AllocateAndInitializeSid / COMCTL32.InitCommonControlsEx / GDI32.CreateFontA / msvcrt.__C_specific_handler / SHELL32.ShellExecuteExA / USER32.CreateWindowExA / VERSION.GetFileVersionInfoA / WININET.HttpQueryInfoA。
3. **XX-10-A 静态候选表只有 9 项** → 201 槽 0 命中是结构性必然。

### [已验证] 运行时层面（本次实弹 2/2 次）
- **201 槽逐槽诊断全列**：`Resolved=112, Unresolved=74, ZeroTerminator=15`
- **模块归属**：msvcrt.dll 76 / kernel32 19 / ntdll 5 / user32 7 / wininet 4 / version 1（共 112 resolved）；74 个 Unresolved 槽 `module=none` 且**值全部落在 Themida 段内**（`0x7ff6eb6b1000-0x7ff6ec3d6800`）——即 74 个槽值是 **Themida VM wrapper 地址**，不是已解析 API 地址。
- **192 站点 → 74 个唯一槽，全部是 Unresolved（VM 失败槽），0 个是 Resolved** → 启动路径只引用 74 个 VM 槽。
- **back-fill 路径**：74 个 Unresolved 全部 `static_original`（原导入表候选）0 命中；112 resolved `live_trace`；15 separator。**XX-10-A 静态回溯 0 覆盖的原因 = 74 个启动槽值是 VM wrapper 地址，9 项明文原导入表（GetProcAddress 解析地址）无法命中任何 VM 地址**。
- **shell trace 74 槽全部失败**：`first pass failed (tracing completed but no API resolved) → deepened retry 仍失败`，无 HitVm 无 FoundApi——trace 起点是 VM wrapper 地址但主线程未在对应地址执行单步，无单步事件到达（R5 的 TID mismatch 正是此表象；本次已改为 slot-scoped 使 201 槽全部遍历，resolved=0 failed=74 skipped=127 accounted=201/201）。

### 结论（[已验证] 上述数据 + [推断] 机理）
XX-10-A 0 覆盖的**结构性根因**：本样品启动路径 IAT 槽值是 Themida VM 包装器（段内地址），静态回溯（原导入表 + GetProcAddress）只能覆盖已解析 API 地址，对 VM 包装器地址结构性 0 命中。真正的解析路径是 shell 侧单步 trace，但 trace 需在正确的执行线程/地址上单步（当前 main_thread 不执行 VM wrapper，导致无单步事件）。**这不是回溯深度不够，是槽值形态（VM wrapper 而非 API 地址）+ trace 执行线程错位**。
