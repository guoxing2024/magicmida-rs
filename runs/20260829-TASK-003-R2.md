## 一、改动摘要（分类器新逻辑 + NOTE 措辞改动）

工作副本里的 `tools/check_clippy_baseline.ps1` 在第 1 轮修改基础上，已包含第 2 轮返工要求的两处修正。本回合我对四条验收标准逐一**实跑验证**，未再对脚本做额外修改（脚本相对 HEAD 的 diff 即第 2 轮修正本身：`+192 / -6`）。下面说明当前生效的逻辑。

### 1. 分类器：按 `code` 前缀三分（修复第 1 轮致命 bug）

对每条 `level:"error"` 的 `compiler-message` 诊断，按其 `message.code.code` 三分：

| `code` 形态 | 归类 | 是否放行继续比基线 | 理由 |
|---|---|---|---|
| 无 code（`null`，如链接失败） | 编译/链接失败 | 否 → `analysisFailed` | clippy 根本没产出可信的 warn 计数 |
| `clippy::` 前缀（如 `clippy::let_unit_value`） | deny 级 clippy lint 命中 | **是**，放行 | 分析已跑完，warn 基线仍是有效测量（工单要求的合法场景） |
| 其他：E 前缀（`E0308/E0277/E0432…`）或 rustc lint 名（`unused_variables`/`unused_unsafe`…） | 编译失败 | 否 → `analysisFailed` | 真正的编译错误被第 1 轮当成 deny 命中放行，是打回根因；rustc 自身 lint 被 `-D` 提升为 error 时，其诊断被移出 warn 桶，使真实回归被读成绿，同样判定为失败 |

第 1 轮的 bug（"有 code 就当 deny 命中"）因此被堵死：`E0308` 等非 `clippy::` 的 code 全部落入"编译失败"桶，不再被误判为合法 deny 命中。

辅助信号（仅当 `analysisFailed` 已成立时才追加理由，绝不单独触发失败）：JSON `build-finished success=false`、退出码 101/1、"跑完零 clippy 警告"、`cargo` 无任何 JSON 输出。这样 deny 命中（分析完成、仅 `success=false`）不会被误杀。

### 2. NOTE 措辞改动（工单具体要求第 4 条）

- 原误导性 `NOTE: cargo clippy exited 101 (deny-level lint present).` 已删除。
- 改为两行**不预设原因**的措辞：
  - `NOTE: N error-level clippy lint diagnostic(s) classified as deny-level lint hits (analysis completed).`（仅陈述分类结果，不猜原因）
  - `NOTE: cargo clippy exited <code> (non-zero) but completed analysis; continuing with the warn-level baseline comparison (cause not assumed).`

3. **"rustc lint 被 `-D` 提升为 error"（如 `unused_variables`）的归类。** 当前分类器把它归入"编译失败"桶（非 `clippy::` 前缀 → 不放行），与 `E0308` 同处理。这与工单返工要求"其他 → 编译失败"一致，且脚本注释写明了理由；本回合未单独实跑这一支（非四条验收之一），仅经代码与 `E0308` 同分支验证。

4. **复现方式偏离字面"Git Bash / `_enter_msvc_env.cmd`"。** 沙箱禁止 Bash→powershell、PowerShell→cmd 的跨壳调用，故负面用例用"前置 Git `usr/bin` 到 PATH"、正面用例用"原生复刻 `_enter_msvc_env.cmd` 的 LIB/INCLUDE/`CARGO_TARGET_*_LINKER`"在 PowerShell 内复现，环境语义等价，但未逐字使用工单给的 `.cmd` 包装命令。
