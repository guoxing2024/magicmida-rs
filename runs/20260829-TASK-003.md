## 怎么区分「没跑起来」和「deny lint 命中」（工单具体要求第 2 条三选一）

**选择：组合方案，主判定 = 解析 JSON 输出中的 `"level":"error"` 且不带 lint `code` 的诊断（方案一）+ `build-finished success=false`（方案三的等价物），辅以两条兜底。**

实测过的三种 JSON 形态（原始命令输出见下「探测实验」）：

1. **deny 级 lint 命中**（合法场景，必须放行继续比较）：
   `{"level":"error","code":{"code":"clippy::let_unit_value"}}`，`cargo clippy` 退出 101，
   `build-finished success=false`（实测确认！cargo 对 deny 命中也报 success=false）。
2. **链接失败 / 编译错误**（本机 Git Bash 负面场景）：`"level":"error"` 且 `code` 为 null
   （`error: linking with \`link.exe\` failed: exit code: 1`），退出 101，`build-finished success=false`。
3. **cargo 根本没产出 JSON**（如向未注册的 lint 传 `-D clippy::dbg_macro`，实测 cargo 直接报错
   并退出 0 —— cargo 的已知怪癖）：stdout 为空。

**为什么必须组合：** 单看 `build-finished success=false` 会把场景 1（合法 deny 命中）误杀；
单看退出码会把场景 1 和 2 一起误杀。所以：

- **主判定**：`error` 级诊断**不带** lint code 的数量 > 0 → 编译/链接失败，`exit 3`。
  deny 命中必然带 code，永不会误伤。
- **辅判 A**：`build-finished success=false` **且**存在无 code 的 rustc error → 追加失败原因
  （单独出现不判失败，因为 deny 命中也触发它）。
- **辅判 B**（兜底）：stdout 完全为空且无 build-finished 记录 → 判「cargo 没跑起来」，`exit 3`。
- **辅判 C**（兜底）：有 build-finished 且分析完成但解析到 0 条 clippy warning → 诊断流异常，`exit 3`。

附带一个行为等价的小改动：`cargo clippy` 命令现在透传 `$env:CARGO_CLIPPY_EXTRA_ARGS`，
使 CI 的 `-D clippy::*` 阶段（ci.yml 中 `-- -D clippy::dbg_macro` 等）与 WO-23 门禁共用
同一 clippy 调用形态，保证「deny 命中」在真实 CI 中与本地验证路径一致。该变量默认未设置，
`@($null -split ' ')` 展开为空数组，行为与原脚本完全一致。

> 说明：本机 Git Bash 的 `PATH` 中 `link.exe` 被解析为 GNU coreutils（工单所述），因此
> 在本机**无法**真实构造「MSVC 环境下 deny 命中」的代码级验证；上述 deny 命中形态通过
> `CARGO_CLIPPY_EXTRA_ARGS="-- -D clippy::let_unit_value -D clippy::type_complexity"` 在
> MSVC 环境下注入验证（见下），deny 诊断与 CI 的 `-D` 阶段形态完全一致。
